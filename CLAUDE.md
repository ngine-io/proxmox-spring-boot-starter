## Commands

```sh
./mvnw verify                                             # build + all tests
./mvnw -pl proxmox-client test                            # one module
./mvnw -pl proxmox-client test -Dtest=ProxmoxClientTests  # one test class
./mvnw -pl proxmox-client test -Dtest='ProxmoxClientTests#mapsErrorsToProxmoxApiException'
./mvnw install -pl proxmox-client                         # needed before testing autoconfigure alone (-pl), since it depends on the client artifact
```

`LiveProxmoxTests` is skipped unless `PVE_URL`, `PVE_TOKEN_ID` and `PVE_TOKEN_SECRET` are set (`PVE_INSECURE=true` for self-signed certs). It also clones/starts/stops/deletes a VM when `PVE_NODE` and `PVE_TEMPLATE_VMID` are set — that test mutates a real cluster.

## Project

Typed Proxmox VE API client + Spring Boot starter. Group ID and base package: `io.ngine.proxmox`. Java 21, Spring Boot 3.5.x (BOM imported in the parent POM, not `spring-boot-starter-parent`). License Apache-2.0.

PVE4J was deliberately rejected (GPL-3.0 conflicts with permissive/proprietary distribution). Do not add GPL dependencies.

## Architecture

Three modules:
- `proxmox-client` — usable without Spring Boot; depends only on `spring-web` and Jackson.
- `proxmox-spring-boot-autoconfigure` — `ProxmoxAutoConfiguration` (active only when `proxmox.url` is set) and `ProxmoxHealthContributorAutoConfiguration` (actuator optional). The client dependency is `optional` here; registration is in `META-INF/spring/...AutoConfiguration.imports`. Configuration metadata is generated by `spring-boot-configuration-processor`, so property Javadoc becomes IDE docs.
- `proxmox-spring-boot-starter` — POM-only aggregator.

Client request flow:
- `ProxmoxClient.Builder.build()` clones the given `RestClient.Builder`, sets base URL `<url>/api2/json`, installs `ProxmoxApiException::raise` as the default status handler, and adds one auth interceptor: `ApiTokenInterceptor` or `TicketInterceptor`.
- `TicketInterceptor` logs in through a separate `RestClient` cloned *before* the interceptor is added (avoids recursion), caches the ticket for 90 min, sends `CSRFPreventionToken` on non-GET requests, and on a 401 renews the ticket and re-executes the request once.
- All endpoint classes (`NodesApi`, `ClusterApi`, `GuestApi` → `QemuApi`/`LxcApi`, `StorageApi`, `TasksApi`) go through package-private `ApiSupport`, which unwraps the `{"data": ...}` envelope (`PveResponse`) and encodes parameters the Proxmox way: form-encoded bodies for POST/PUT, query params for GET/DELETE, booleans as `0`/`1`, collections comma-joined, nulls dropped. New endpoints should use `ApiSupport` rather than `RestClient` directly.
- Async operations return `Upid`; `TasksApi.await` polls `/nodes/{node}/tasks/{upid}/status` (node taken from the UPID) and treats `OK` and `WARNINGS: n` as success.

Proxmox API quirks handled in `model/`:
- Booleans arrive as `0`/`1` or strings — annotate `Boolean` record components with `@JsonDeserialize(using = PveBooleanDeserializer.class)`.
- Numbers sometimes arrive as strings (e.g. `/cluster/nextid`); Jackson coerces them.
- Guest config keys are open-ended (`net0`, `scsi0`, …), so `GuestConfig` wraps a map with typed accessors instead of being a record.
- Records use `@JsonIgnoreProperties(ignoreUnknown = true)`.
- Error messages come in the HTTP reason phrase or a `message` field, field errors in `errors`.

TLS: the preferred setup is `proxmox.ssl.bundle` (Spring SSL bundle with the PVE CA). `proxmox.ssl.insecure` swaps in `InsecureClientHttpRequestFactory` (trust-all, `HttpURLConnection`-based) and logs a warning.

## Testing conventions

- Client tests bind `MockRestServiceServer` to a `RestClient.Builder` and pass that builder to `ProxmoxClient.builder().restClientBuilder(...)`. Path variables are URL-encoded, so UPIDs appear as `UPID%3Apve1%3A...` in expected URIs.
- Auto-configuration tests use `ApplicationContextRunner`; the end-to-end test uses a JDK `HttpServer` because auto-configuration replaces the request factory, which would bypass a mock server.

## Releasing

Pushing a `v*` tag runs `.github/workflows/release.yml`. It sets the version from the tag (`v0.1.0` → `0.1.0`), then runs `./mvnw -P release deploy`, which signs with GPG and uploads to the Maven Central Portal. `autoPublish` is `false`, so each deployment waits in the Portal for a manual "Publish". The workflow expects the org secrets `CENTRAL_TOKEN_USERNAME`, `CENTRAL_TOKEN_PASSWORD`, `GPG_PRIVATE_KEY` and `GPG_PASSPHRASE`. The starter has no code, so its sources and javadoc jars are built from `src/main/placeholder`. The setup mirrors `ngine-io/cloudscalech-spring-boot-starter`.
